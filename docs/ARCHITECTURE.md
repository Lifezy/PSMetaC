# 安全与架构

## 组件职责

- **桌面程序**：用户设置、任务创建、队列、报告、隔离区和通知。
- **CleanerService**：所有入口共享的受控业务接口。
- **JobWorker**：唯一允许调度 Photoshop 的单任务执行器。
- **SQLite**：保存任务、状态、幂等编号、收件目录和事件。
- **MCP stdio 适配器**：把受控 MCP 工具转发到本地命名管道。
- **Photoshop JSX**：默认处理工作副本；只有任务明确选择 `in_place` 时才直接处理源文件。链接智能对象始终只记录和跳过。

MCP 不直接调用 JSX，也不能传入脚本路径。

桌面程序使用 Electron 单实例锁：再次启动时不会建立第二套队列，而是把已经
打开的窗口带到前台。数据目录另有带进程号和有效期的执行租约；即使另一个
命令行执行器绕过桌面入口，也不能在同一数据库上恢复或运行第二个任务。预检
子进程强制使用 Electron 的 Node 模式，不会再产生多余的 GPU 和渲染器进程。

## 路径授权模型

路径授权分成两类，不能互相冒充：

- **桌面精确选择**：主进程记录文件选择器返回的精确文件和目录。渲染页面只
  能为这些路径创建手动任务；授权结果随任务写入 SQLite，不扩大全局白名单。
- **允许目录**：供 MCP 和监控目录等无人值守入口使用。输入、输出均必须在
  配置范围内。

用户可配置排除目录，默认为空。排除目录优先于上述两种授权。配置版本 3 会
在首次加载旧配置时移除旧版本强制写入的 `E:\Work` 项，同时保留其他允许
目录；之后用户仍可按自己的需要重新把任意目录加入排除列表。

手动任务之所以不直接把父目录加入允许列表，是因为“选择一个文件”不等于
“允许 MCP 和监控处理这个目录下未来出现的所有文件”。精确授权多记录两个
布尔字段：源文件是否由桌面选择、输出是否由桌面选择，供崩溃恢复后的执行
阶段继续使用相同边界。

## 自包含发布结构

发布版不依赖开发目录旁边的 `psb_batch_tool`。四个已经验证的检查、JSX、
像素比较和 VBS 文件保存在 `vendor/psb_batch_tool`，清单固定文件大小和
SHA-256；构建后还会再次核对。好处是安装到另一台电脑后执行逻辑不会缺失，
也不会意外拿到开发目录中新改但未验收的脚本；代价是每次正式更新这些文件
都必须同步更新清单并重新跑回归。

任务账本使用 Electron/Node 内置的 `node:sqlite`，没有额外原生数据库插件。
这减少了安装包中不同 Node ABI（二进制接口）不兼容的问题；目前该接口仍会
显示实验性警告，所以 Electron 固定为 `43.2.0`，升级 Electron 前必须重新跑
数据库、崩溃恢复和安装包测试。

## 打包完整性

构建流程先在 `.runtime-app` 生成只含运行代码和精简清单的暂存目录，再创建
`app.asar`。ASAR 可以理解为 Electron 的只读应用归档。构建钩子把 ASAR
头部的 SHA-256 写回 EXE 的 `ELECTRONASAR` 完整性资源，随后
`verify-dist.mjs` 独立复核二者相等。

这套自定义步骤解决了当前项目布局下发布清单被打包器遗漏的问题；优点是主
入口和完整性校验可重复证明，缺点是升级 electron-builder 时必须重点复核
构建钩子。不能因为安装包能启动就跳过 `verify:dist`。

## 文件流程

```text
明确文件/收件目录
    ↓
路径与格式检查
    ↓
只读预检 + 源文件 SHA-256
    ↓
策略判断 ── 不符合 → 跳过报告
    ↓
版本、空闲、空间检查 ── 不安全 → 阻止报告
    ↓
逐字节工作副本 + SHA-256 复核
    ↓
仅对工作副本生成严格 ID 清理计划
    ↓
Photoshop 处理 → 同目录隐藏临时输出
    ↓
后检、结构、XMP、处理前后像素验证（按需重新打开）
    ├─ 用户选定的必须项通过 → 新成品（其他失败项作为警告）
    └─ 任一必须项失败 → 人工复核
    ↓
再次计算源文件 SHA-256 + 报告 + 日志
```

临时输出放在最终输出同一卷中，验证通过后使用不覆盖的重命名发布。这样
不会出现跨卷复制到一半却被当作成品的情况。

所有可选验收项都会实际执行。用户的勾选只决定该失败项是否阻止自动发布，
不会从报告和日志中删除未勾选项目的结果。源文件变化、Photoshop 未完成、
越权路径和数据库损坏等基础安全错误不能取消。

### 可选流水线预检

默认按“预检一个文件 → Photoshop 处理该文件 → 再预检下一个文件”串行运行。
用户开启流水线后，可在 Photoshop 处理当前文件时只读预检队列中的下一个文件。
预检严格按任务创建顺序并限制为一个，Photoshop 执行也限制为一个。执行前再次
核对源文件指纹；文件改变时废弃原计划并重新预检。

### 自动处理文件夹

自动处理文件夹由桌面服务定时扫描，不需要 MCP。PSB 首次发现后写入 SQLite，
连续达到稳定等待时间才提交；相同路径、大小和修改时间形成的签名只提交一次。
递归扫描会排除软件数据目录、成品目录和符号链接。PSD 只计入扫描说明，不会由
无人值守规则提交。

### 直接保存原文件分支

`in_place` 是独立的高风险执行分支，不是安全副本流程的隐式降级：

1. 仍执行路径、格式、版本、文件稳定性、源文件指纹、Photoshop 空闲和空间检查。
2. 用户选择备份时，先把源文件复制到数据目录的 `backups\<jobId>`，并复核 SHA-256。
3. Photoshop 直接打开源文件，完成元数据清理后调用原位保存。
4. 不生成另存副本，也不执行保存后重新打开、结构、XMP 或像素校对。
5. 报告必须明确写明源文件已覆盖、备份路径和“未校对”，不能把未知项目显示成通过。
6. 保存开始后不强杀 Photoshop；迟到的取消请求只能在保存安全结束后记录结果。
7. 个别目标智能对象无法处理时，仍保存已经完成的清理，报告标记为“部分完成、未校对”；这不是自动验收通过。

优点是占用空间和总耗时更少，适合用户明确接受风险的批处理。缺点是无法证明
保存后图层和像素完全一致；不创建备份时也无法由 PSMetaC 恢复原文件。

### 队列暂停与终止

- “暂停”先阻止新文件进入执行器；若当前文件已开始预检、复制、清理或验证，SQLite
  会记录该文件为 `finishCurrentJobId`，让它跨阶段安全完成，然后保持暂停。
- “终止”采用相同的完成当前文件规则，并立即把尚未开始的任务标记为取消。
- 暂停后可以恢复；终止后的已取消任务不会自动恢复。
- 两者都不会中途强制关闭 Photoshop，直存保存也不会被强行打断。

## 检查点、取消和重复任务的边界

- **安全断点续传不是 Photoshop 指令级续传。** 程序只在预检完成、工作副本完成、
  Photoshop 返回、验证和发布等持久检查点恢复。Photoshop 正在编辑某个智能对象时发生
  崩溃，重启后不会从对象内部继续，而是核对源文件、事件哈希链和现场文件，再从最近
  的安全阶段重新开始。对正在执行的旧任务，只有此前已经写入持久检查点的阶段有效。
- **取消不能覆盖 Photoshop 正在执行的命令。** `CANCEL.flag` 只能在 JSX 主动检查的
  边界生效。保存、打开智能对象等 Adobe 命令正在执行时，PSMetaC 等待命令返回；强杀
  Photoshop 可能留下半保存文件，因此明确禁止。
- **重复任务保护只阻止意外并发。** 同一源路径已有非终态任务时，桌面、监控和 MCP
  的重复提交返回原任务，避免两份任务同时操作同一文件、重复占用空间或生成冲突结果。
  任务进入终态后，用户仍可明确重新创建任务。
- **外部修改竞争检查必须保留。** 从用户选择到真正交给 Photoshop 之间可能经过长时间
  排队、预检、复制或等待。执行前再次比较大小、修改时间和 SHA-256，避免按旧计划处理
  已被 Photoshop、同步软件或其他程序改过的文件；直存模式尤其不能关闭此检查。

## 智能对象性能策略

- 执行器以父容器为保存单元：同一父容器中的目标完成后统一保存，避免每个子对象都让
  大型父 PSB 重复落盘。
- 正常成功路径只恢复当前目标和 3–5 层祖先链的锁定/可见状态；全图层状态扫描保留给
  异常兜底和最终审计。
- 共享资产只在相同父容器作用域内去重。不能把 `assetId` 做成全局去重键，否则不同
  嵌套路径可能被错误跳过。
- `photoshop.log` 记录对象打开、对象保存、状态恢复、根文档和最终保存耗时，用于识别
  真正瓶颈，而不是只依赖总耗时猜测。

## 计划覆盖策略

- `strict`：任何预检目标遗漏都保留结果并进入人工复核。
- `threshold`：遗漏比例不超过用户阈值时继续按其他验收项判断；超过阈值进入复核。
- `skip`：覆盖差异只写入报告，不单独阻止放行。

三种策略都不会伪造“对象已清理”。报告始终写入计划数、实际覆盖数、遗漏数和比例。

## 可选内容整理

- 删除隐藏/空图层与 XMP 清理是不同风险等级：前者会改变工程内容，因此默认关闭。
- 第一版只接受桌面手动精确选择的安全副本任务；服务层和 JSX 双重拒绝直存，MCP、监控目录和命令行不暴露该能力。
- JSX 只在元数据处理完成后整理根文档图层，不进入链接智能对象；日志逐项记录删除和跳过。
- 空图层判断采用最小可证明规则：普通像素层、空边界、非背景、非剪贴、无用户/矢量蒙版、无图层效果。无法确认时宁可跳过。
- 删除发生后，验证层加入不可关闭的人工复核原因；源文件完整性检查仍是硬门槛。

## 状态

| 状态 | 含义 |
|---|---|
| `queued_preflight` | 等待只读预检 |
| `preflighting` | 正在解析和计算源文件指纹 |
| `preflight_complete` | 仅预检任务完成 |
| `skipped` | 未发现目标或未达到策略门槛 |
| `blocked` | 安全条件不允许执行 |
| `awaiting_approval` | 需要桌面用户明确批准 |
| `ready` | 已满足执行条件 |
| `waiting_photoshop` | Photoshop 有用户文档或状态不明 |
| `copying` | 正在建立工作副本 |
| `running` | Photoshop 正在处理工作副本 |
| `validating` | 正在后检和像素比较 |
| `succeeded` | 所选验收通过或用户明确要求的直存完成，原因代码区分是否校对 |
| `partial` | 直存已保存，但部分目标对象未完成，未做保存后校对 |
| `quarantined` | 生成了副本，但不能当作合格成品 |
| `cancelled` | 在安全检查点取消 |
| `failed` | 未获得可验证输出 |
| `critical_paused` | 源文件变化等严重事件，整队列暂停 |

## 崩溃恢复

- 预检、复制、Photoshop 或验证中断的任务先标记为中断。
- 源文件大小和修改时间仍符合基线、且尚未重试过时，回到只读预检。
- 不从某个智能对象中间继续。
- Photoshop 仍有文档时进入等待，不强制关闭。
- 已存在的 `.partial` 文件绝不直接发布。

## 审计完整性

每个事件保存 `prevHash` 和 `eventHash`。后一个事件的哈希包含前一个哈希，
所以事后修改或删除中间事件可以被检测。数据库和每任务 JSONL 同时保留
事件；身份令牌不会写入日志。

桌面中的“从列表移除”是软删除：任务会从日常列表隐藏，但成品、问题副本、
报告、逐步骤日志和最小审计记录都会保留。正在检查、复制、清理或验证的任务
必须先完成安全取消，不能直接移除。MCP 不提供删除或移除接口。

已结束任务另有桌面专属的“删除任务资料”：二次确认后只删除数据目录中的
权威报告、任务 JSONL 和临时工作区。源文件、成品、问题副本，以及结果旁的
随附报告不删除；全局审计日志保留不含原路径的删除墓碑。MCP 同样不能调用。

## 版本边界

当前完整实机验收白名单只有 Photoshop `26.11`。其他已安装版本不再被版本号
阻止：用户可以预检、人工批准或在自有沙盒中执行全流程，任务、报告和诊断日志会
明确标记“尚未验证”。运行成功不等于正式支持；将新版本加入正式支持清单前，
必须用可信样本重新运行结构、取消、保存、智能对象、像素和恢复回归，并留下可复核
报告。程序不会仅凭一次启动、COM 握手或单文件保存成功自动扩大正式支持范围。
